# Metallic-RC — standing authorization and working instructions

Recorded October 22, 2026, at the owner's request:

> Write some things so that you don’t have to ask for my permission every time on the RC project

## Default: continue the requested work

For an assigned **Metallic-RC** task, proceed independently through routine investigation, implementation, debugging, builds, tests, repairs, and reversible project maintenance. These necessary steps do not need another conversational confirmation. Do not stop to ask "Should I continue?" or repeat a permission request the owner has already answered.

Use the newest owner instruction, compatible earlier owner decisions, and verified project evidence. Choose reasonable implementation details when the intended outcome is clear. Keep working until the assigned outcome is complete or a concrete external blocker prevents it. Progress updates are informational; they are not approval requests.

Scope is Metallic-RC's own backend, launcher, compatibility code, development tools, and analysis of the owner's local 2026 Rec Room copies. This instruction does not expand a task to unrelated projects, machines, or accounts.

## Routine actions already within scope

- Read relevant source, configuration, logs, crash reports, documentation, and project history. Research technical questions and use available debugging, REA, and analysis tools within their existing access.
- Create and edit project code, scripts, tests, documentation, and project configuration. Refactor or repair code and resolve conflicts while preserving unrelated work.
- Build and run authored software, targeted tests, synthetic fixtures, and local development services; diagnose failures and repeat meaningful verification. Honor existing client-test profiles, integrity checks, process ownership, time limits, and attachment/elevation boundaries.
- Add ordinary free dependencies from trusted sources in the project or an isolated user-level environment when necessary. Avoid global upgrades or administrator-level installation when a project-local approach is sufficient.
- Start, gracefully stop, or restart clearly identified Metallic-RC development processes when needed. Use existing project supervisors and recovery mechanisms; preserve service data and rollback options.
- Create backups, checkpoints, branches, and isolated worktrees. Commit project changes, push an appropriate work branch, and create or update draft pull requests under the existing review workflow.
- Remove and regenerate clearly identified disposable build outputs and project caches when source, saves, original client files, backups, and required evidence are unaffected.
- Maintain concise handoff notes stating what changed, what was actually verified, the next step, and any remaining blocker.

These examples clarify routine work; they do not authorize unrelated access or a new, more invasive native-client technique.

## Preserve originals and existing controls

Keep the original installed and fresh 2026 client copies, irreplaceable evidence, user data, and unrelated edits intact. Work on copies when an operation could modify original files. Back up meaningful project state before a potentially disruptive reversible change.

Use hidden/background, noninteractive terminals where supported, with output captured to logs. Do not open unnecessary foreground consoles or leave invisible commands waiting for Enter. Ordinary application windows and Windows approval dialogs are separate from this preference.

Keep work on branches and draft PRs until the applicable review and CI gates are met. This instruction does not grant blanket merging, release, deployment, or branch-protection authority. Check current repository visibility before publishing; upload only appropriate authored source and sanitized documentation, never private client binaries, dumps, credentials, full game logs, or account databases.

Preserve required operating-system prompts, tool approvals, access controls, sandbox rules, and the existing native-client safety gates. Never auto-click consent, disable protections, silently elevate, or change those controls to eliminate prompts. An existing approved test profile is not approval for arbitrary new targets or methods.

## Ask only when genuinely new authority is needed

First check the current task and earlier owner authorization. If the specific action is already authorized, do not ask again merely because this document lists it as consequential. Otherwise, obtain approval before:

- Spending money, starting a paid service, increasing billing limits, or accepting a new contractual commitment.
- Irreversibly deleting or overwriting originals, irreplaceable evidence, backups, real-user data, or unrelated work; discarding someone else's edits; force-pushing or rewriting shared history.
- Merging or publicly releasing changes without established authorization, exposing a new public endpoint, or making a live-service change that materially affects other users.
- Changing machine-wide security, administrator access, firewall/DNS/network settings, account permissions, credentials, or remote-access configuration beyond the existing authorized scope.
- Sending messages or invitations to other people, sharing private material with a new recipient, or expanding the work into a materially different project.

Complete all authorized preparation and independent work before asking. State the exact remaining action, its purpose, consequence, and why existing authorization does not cover it. If a skill, repository rule, operating-system prompt, or automatic approval review is the blocker, identify it plainly.

If the owner is unavailable, continue independent work that remains authorized, preserve a usable checkpoint, and report the blocked step once. Do not repeatedly relaunch the same approval prompt or treat silence as consent.

## Report actual outcomes

Distinguish implemented code, passing synthetic tests, working local services, verified original-client behavior, and released functionality. Do not describe backend or fixture success as proof that original-client login, gameplay, or voice works.
