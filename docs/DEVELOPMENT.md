# Metallic Studios — Development and Progress Tracking Rules

## How project progress works (already implemented)

The repository has a self-updating issue dashboard: [PROGRESS.md](PROGRESS.md) and [progress.json](progress.json) are generated by [scripts/update_progress.py](../scripts/update_progress.py), validated by [tests/test_progress.py](../tests/test_progress.py), and refreshed by [GitHub Actions](../.github/workflows/update-progress.yml).

The workflow runs on issue open/edit/close/reopen/label events, on relevant workflow/script changes, via manual dispatch and daily reconciliation. It queries the current repository's GitHub Issues API, skips pull requests, classifies titles starting with \`[P0]\`–\`[P6]\`, and reports the number of closed work items.

**This is a count of deliverables closed, not a claim that the game is playable.** We deliberately do not assign percent-complete guesses to tasks or automatically count all research notes as shipped functionality.

### Write issues correctly

Title convention:
- \`[P0] Research & architecture decision\`
- \`[P1] Back-end feature / launcher\`
- \`[P2] Gameplay, avatars or dedicated server\`
- \`[P3] Creator workflow and Circuits V3\`
- \`[P4] Community safety and marketplace\`
- \`[P5] Partner federation and ports\`
- \`[P6] Hardening, QA, public release\`

Every tracked issue needs: objective, dependencies, player benefit, acceptance conditions, test method, evidence link, and owner where practical. Unscoped questions can remain normal issues (they are intentionally not counted).

When created in the GitHub UI, you can apply the following *optional* labels after they have been created in the repository:
- \`status:in-progress\` for active work.
- \`status:blocked\` for work stopped by a named dependency.
- \`area:game\`, \`area:backend\`, \`area:creator\`, \`area:launcher\`, \`area:infra\`, \`area:ui\`, \`area:research\` for filtering.

The script recognizes the two status labels, but **GitHub repository labels must actually exist before label assignment**. It does not silently pretend unsupported labels are present.

### PR review checklist

- [ ] Linked issue and design/ADR where architecture changes
- [ ] Clear reproduction steps and acceptance tests
- [ ] Passing typecheck, lint and unit/integration tests
- [ ] Networking changes measured against simulated packet loss and latency
- [ ] Database changes include migrations and rollback validation
- [ ] Permission, secrets, moderation and import path reviewed
- [ ] UI/VR work tested for input parity, contrast, motion comfort, alignment, responsive screens
- [ ] Deployment, crash/rollback path and new observability dashboards documented
- [ ] Screenshots/videos/profiling traces or reproducible build artifact attached

### Review process

1. Pick the earliest unblocked issue on the dependency path in [ROADMAP.md](ROADMAP.md).
2. Mark it active (optional label) and create a branch tied to that issue.
3. Make changes, run tests, and open PR with evidence.
4. Review against acceptance criteria. Do **not** close feature issue merely because draft code exists.
5. Merge only after CI passes, then close the task and let the dashboard update.
6. At every playable milestone, post a specific build artifact and [release acceptance evidence](#release-evidence), separately from issue completion.

### Release evidence

Before describing any feature as 'released', attach a release-evidence record with:

\`\`\`json
{
  "feature": "P2-two-player-room",
  "build": "0.1.0-alpha.1",
  "commit": "full_git_commit_sha",
  "artifact_url": "https://github.com/owner/repo/releases/...",
  "platforms_tested": ["windows-x64", "pcvr-openxr"],
  "test_result_url": "https://github.com/owner/repo/actions/runs/...",
  "performance_capture": "per_device_trace_or_dashboard",
  "acceptance_result": "passed"
}
\`\`\`

These are schema examples only. Until an actual signed artifact and tests exist, user-facing capability remains **planned** or **in development**.

### How to consume progress on the future Metallic website

The site can display sanitized values from [progress.json](progress.json) (counts, phase names and last issue update). Since the repository is **private**, the website must not directly embed the private GitHub file without access controls. A future publishing workflow should copy only allowed aggregate fields to a public endpoint; never leak internal issue names, source code or auth tokens.

### Progress updater test commands

\`\`\`shell
python -m unittest discover -s tests -p 'test_*.py' -v
GITHUB_TOKEN="a_repo_scoped_issues_read_token" GITHUB_REPOSITORY="oncoursemail/Metallic" python scripts/update_progress.py
\`\`\`

Use a private environment variable, not a pasted token in GitHub issues or docs. In GitHub Actions, the built-in \`GITHUB_TOKEN\` is provided automatically with only required rights. The script also supports \`--fixture tests/fixtures/issues.json --output-dir /tmp/progress\` for offline fixture generation.

### Operational note

A GitHub Actions workflow push via \`GITHUB_TOKEN\` does not trigger a new push workflow. This prevents the updater from recursively updating itself: [GitHub official explanation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow). A daily reconciliation also handles missed issue events. The action should remain inexpensive, but private-repository Actions limits and platform policy are not unlimited.

## Reporting standard

Each weekly engineering update should state separately:
- **Added:** tests, docs, implementation, and issues opened.
- **Passing:** verifiable CI jobs and artifact run links.
- **Working in a build:** proven gameplay/user-facing capabilities.
- **Blocked:** missing dependencies, data, device access, or hosting.
- **Next:** one highest-priority vertical slice.
- **Measured:** hardware performance, networking and server costs with date/assumptions.

No 'highest performance' claim is meaningful without hardware, scenario and benchmark comparisons.
