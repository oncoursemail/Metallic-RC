# Authored-worker process adapter

Board 350. This isolated crate exercises non-admin Windows process plumbing with a fixed authored sibling executable. It does not execute Rec Room, attach Frida, open WFP, request elevation, contact accounts, start services, or enable the original-client planner. It is a test tool, not an execution broker or a complete security sandbox.

The only worker path is `metallic-owned-adapter-worker.exe` beside the checker. The caller must supply a SHA-256 value from its reviewed build. Missing or malformed values refuse execution. The checker never computes a sibling digest and treats that as permission. The supplied digest is local identity data, not independent attestation or a security grant. Source/build review remains separate.

The adapter holds read locks denying write/delete on the worker and its directory ancestors, rejects reparse directories, hashes at most 16 MiB, and refuses a changed pin. It creates the child suspended with an explicit Unicode environment containing only the existing 20 allowed names, including SystemDrive. Values are not logged. An explicit STARTUPINFOEX handle list contains only stdin and the two output writers; parent pipe read ends are noninheritable. Retained process-image identity is checked against the locked file's volume/file ID. Assignment to a fresh kill-on-close job without breakaway and membership verification precede caller-controlled resume. Double resume is refused.

Each run creates a private directory beneath the current user's LOCALAPPDATA/Metallic-RC/owned-process-adapter-checks. Fresh directories use a protected, inheritable owner-SID-only DACL. Existing directory ACLs are not changed. Directory handles remain held against rename while private evidence is written. A create-new `summary.json` records only numeric process/output facts and prefix hashes, never environment values or worker output text.

Stdout and stderr drain concurrently through separate noninherited read ends. Each retains at most a 65,536-byte prefix in memory and records a SHA-256, byte count and EOF; additional output is drained without retention. Observation is capped at five seconds, retained-process/job cleanup at two seconds, with bounded drain completion. These are authored test bounds, not the original-client 90/30/130-second experiment. Cleanup targets the retained process and its constructed job, including inherited descendants, never a name or PID search. Pre-cleanup exit and timeout facts remain separate from cleanup termination code 124. Cleanup ownership is established immediately after successful CreateProcessW, before job admission, image checks or drain startup can fail. Drain threads use fallible Builder::spawn. Drop attempts bounded retained-process/job cleanup and completes already-started drains on errors and interrupted admission.

The closed worker roles are marker, environment-presence counts, simultaneous stdout/stderr flood, wait, and a same-worker grandchild. Unknown worker arguments fail. The internal checker owner-death role creates only one fixed wait worker, publishes its owned PID, waits for the test parent's bounded acknowledgement, then exits without Rust Drop. The parent first retains and verifies that worker image, then confirms the retained process terminates when the OS closes the last job handle. This is a single-worker owner-death control. The separate timeout control waits for the fixed grandchild marker before termination, then checks the constructed descendant job, exact marker, job emptiness and pipe EOF; it does not establish an independently identified grandchild inventory.

An early owner-death test assumed every returned job PID was an authored worker. It correctly failed image admission when Windows included `conhost.exe`. No comparison was relaxed; cleanup remained on the constructed job and retained handles, not an unverified PID. Background creation flags were made explicit, and the owner-death test was narrowed to a one-worker job whose membership is checked before handoff. The failed test is not counted as a pass or as proof of an image-query representation defect.

Prepare and review the source/build, then use the expected worker digest as data:

```powershell
cargo build --offline --locked --release --bins
cargo test --offline --locked --lib
.\target\release\metallic-owned-adapter-check.exe --plan
.\target\release\metallic-owned-adapter-check.exe --self-test $reviewedWorkerSha256
```

Only cached windows-sys 0.61.2/windows-link 0.2.1 are used; Cargo.lock records registry checksums. No dependencies or toolchain components were installed. Four pure unit tests passed. The initial seven Windows checks passed, but independent review then found that infallible thread startup could panic before cleanup ownership existed. Those seven passes did not cover that failure. The corrected non-elevated Windows self-test passed nine checks: wrong-pin refusal; suspended silence/image read-lock/double-resume/marker handling; environment scrub; simultaneous 2 MiB output on each stream with bounded prefixes, independently computed known SHA-256 vectors and EOF; unresumed cleanup; timeout/descendant job cleanup; single-worker owner death; and forced first/second output-drain startup failures. Each injected startup failure requires the exact failure result, retained-child exit 124, an empty constructed job, zero output bytes, no active drain threads, EOF for any drain that started, and completion within five seconds. The output explicitly retains `originalClientTested: false` and `executionReady: false`.

This proves only the tested owned-worker paths. It does not establish adversarial same-user isolation, arbitrary program compatibility, complete process-tree image inventory, network containment, or original-client readiness. No active profile, existing spawn API, shared fixture crate, existing production workflow or STAR source was changed. A separate focused CI workflow was added.

The focused workflow builds locked binaries, runs the four pure tests and checks the exact inert plan on Windows and Ubuntu. On Windows it supplies the digest of that CI build as identity data. If the actual token is elevated, the existing native token gate must return its exact refusal before worker creation; this does **not** count as nine worker controls. If the actual token is not elevated, all nine closed controls must pass. GitHub [documents administrator execution with UAC disabled on hosted Windows VMs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#administrative-privileges), so the expected hosted coverage is build/pure/plan plus elevation refusal. The nine standard-user controls reported above were actually executed locally. The workflow creates no users, brokers, token substitutions or protection changes, and publishes no private receipts or binaries.
